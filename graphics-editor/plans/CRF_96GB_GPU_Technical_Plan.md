# CRF 96 GB GPU 技术升级方案

**面向 RTX PRO 6000 96 GB 的原生图形计算、材质与细节优化**

- 日期：2026-11-22（北京时间）
- 状态：技术设计提案；尚未连接用户服务器，未完成 GPU 性能或画质实测
- 版本关系：参考用户 1.2 实验报告提出的 GPU96 开发设计；当前实际代码基线为 `55103cc7399cef3bb5eb7d9e7875f3785dedd9cd` 的 1.1.0-experimental.2 对象函数和 quality12 参考重建实现；quality13 另有冻结设计/合同，须继续实现。报告中的两个提交尚不能在本仓库解析。GPU96 不代表已发布的 1.3，历史版本和完成状态保持不变。
- 资源前提：用户已有一张云端 RTX PRO 6000 / 96 GB；以实际设备可见资源为准
- 主线：模型生成程序，CRF 自己的函数和算子计算图片与视频；GUI Service、Agent Harness、Compute Kernel 保持同一套场景语义

当前入口：[整体计划](CRF_Integrated_Development_Plan.md) · [活动任务账本](CRF_Integrated_Execution_Plan.json) · [基线核对](../verification/GPU96_BASELINE_STATUS.md) · [Codex 启动](../CODEX_START_HERE.md)。本方案 GPU 阶段使用 `GPU-M*`，原 1.1 阶段使用 `V11-M*`。

## 1. 决策摘要

这次按整卡图形计算设计：把对象几何、材质函数、多尺度细节、拟合状态、采样队列和候选评价组织成 GPU 常驻工作集；让可用资源随任务规模扩展，而不把系统固定成只能使用少量显存的单对象演示。

**96 GB 的主要用途是更复杂的场景状态、更充分的优化和更高吞吐的成像计算。** 默认沿用已有模型提议服务，云卡不预留大语言模型权重。需要自部署模型时另设推理阶段，明确它与渲染争用的显存及 GPU 时间。

高负载配置以设备实际可见显存的约 85%–90% 作为可探索的容量区间，默认保留至少 10% 的整卡余量，并按实测临时峰值扩大。这个区间是容量策略，不是必须占满的合格线。已饱和计算或内存带宽的小工作集可以更高效；在这种情况下，应提高有效任务吞吐，或记录继续扩容不再有收益的证据。不得用无效张量、重复模型、重复资产或无收益的候选把数字做高。

本轮交付必须同时回答四个问题：

1. GPU 是否真实执行 CRF 的拟合与渲染？
2. 增加计算量是否改善几何、材质、光照、细节或编辑质量？
3. 更大的工作集是否提高同预算画质或吞吐？
4. 这些能力是否能从工作台调用、取消、恢复、重放和继续编辑？

**工程验收以可复现的图片、性能轨迹、质量曲线和完整工作流为准。** 当前没有依据承诺任意场景照片级、4K 实时或固定加速倍数。

## 2. 当前证据与能力边界

### 2.1 已有基础

用户提供的《CRF 1.2 技术完成报告》记录了两个固定视角实验，输出为 640 × 400。作者协议包含 profile、ellipse、tube 三类形状操作，材质接口主要暴露颜色与粗糙度；正式作品来自独立 Codex 作者上下文，另有一次本地 Qwen3-4B 高度补丁调用。实验支持程序导入、有限形变、光源变化和视频重放。[P1]

报告给出了 Python、NumPy、Pillow、ffmpeg 实验路径，但未提供云端 CUDA 性能轨迹、GPU 显存分解或内核利用率。这是尚未提供证据，不是对完整仓库“绝对没有 GPU 实现”的断言。

原 1.1 计划要求 CPU 参考路径、GPU 数值符合性、计算内核改进、证明义务、真实程序级 RSI 收益和可运行编辑器同时成立。本提案继续保留这些要求。[P2]

### 2.2 本轮明确扩展的内容

| 层面 | 当前报告支持的范围 | 本轮拟新增 |
| --- | --- | --- |
| 几何 | 固定视角的有限形状组合与整体高度变化 | 对象/部件层级、局部坐标、轮廓函数、局部深度、法线、接触与遮挡 |
| 材质 | 颜色、粗糙度接口 | 固有色、微表面方向、粗糙度场、金属/非金属响应、多尺度程序细节 |
| 光照 | 已有固定场景光照实验 | 面积光、显式可见性、受限换光；空间函数扩展后再处理完整反射/透射与间接光 |
| 拟合 | 既有参数拟合路径 | 多对象并行拟合、分阶段求解、对象局部小网络和保留观测验证 |
| 输出 | 640 × 400 和短视频 | 原生 2048 级长边与 3840 × 2160 输出、尺度一致性和时序一致性 |
| 资源 | 无整卡测量证据 | 设备探测、显存账本、GPU 时间线、动态批处理、容量与质量对照 |
| 交互 | 实验入口与报告 | GUI 提交、预览、进度、取消、恢复、版本比较与证据查看 |

### 2.3 保持原生 CRF 路线

最终像素由冻结版本的 CRF 内核，根据场景程序及声明的函数资产计算。参考照片是观察和拟合输入；其身份、来源、用途和派生资产全部记录。

禁止把源照片、来源不明的整幅 RGB 残差或外部完整生成图直接作为最终结果，随后声称是可编辑的几何/材质生成。二维外观重建可以作为合法能力保留，但必须标为“外观重建”，不能据此宣称材质与光照已分离。

本方案不调用 Blender 或其他外部三维产品流水线作为最终产图器。若引入 CRF 自己的空间查询函数，需明确新增的表示和能力范围，见第 6 节。

### 2.4 对象小网络的训练范围

用户新提出的对象级小网络纳入本方案。优化其权重在数学上属于训练，不能用“拟合”一词隐去这一事实。

范围限定为逐对象、逐观察或逐资产的小网络/特征参数；基础语言模型和视觉模型保持冻结，不更新跨场景共享基础模型权重。此项相对于旧计划的限制是明确的范围扩展，需要在资产元数据中记录训练输入、目标、参数数量、训练成本与适用域。

## 3. 硬件和软件基线

### 3.1 先识别实际云卡

NVIDIA 官方列出 RTX PRO 6000 Blackwell 的 Server、Workstation 和 Max-Q 版本，均为 96 GB GDDR7 ECC，但功耗与散热配置不同。仅凭“96 GB 云卡”不能推定具体版本、独占状态、功率上限或实际显存可用量。[R1]

实施阶段只读记录：

- GPU 完整名称、UUID、Compute Capability、实际可见显存字节数。
- 是否为完整 GPU，是否存在 MIG/vGPU 切分、其他驻留进程或共享配额。
- 驱动、CUDA runtime、PyTorch 与扩展构建版本。
- 功率上限、时钟与降频原因；不自动修改云服务商的功率或隔离配置。
- CPU 核数、主机内存、磁盘和实际数据传输表现。

该系列的 Compute Capability 为 12.0，即 sm_120；旧 GPU 的预编译算子不能仅因“支持 CUDA”就视为兼容。[R2]

### 3.2 最小主计算栈

**主路径：现有场景程序 → 统一算子 IR → PyTorch/CUDA 张量后端 → 经剖析选择的 Triton/CUDA 热点 → 图片、视频与证据。**

PyTorch 官方已提供 Blackwell 支持路径。实施时锁定当前经过目标服务器验证的稳定组合，不机械沿用旧环境，也不把早期支持公告的版本号当成当前推荐版本。[R3]

| 组件 | 职责 | 引入条件 |
| --- | --- | --- |
| Python 服务与 PyTorch/CUDA | 张量数据、可微拟合、统一设备管理、第一版 GPU 算子 | 必需 |
| torch.compile | 减少图解释和部分算子调度开销 | 正确性通过后实测启用 |
| Triton 或 CUDA C++ | 覆盖求值、tile 累积、特征求值、损失归约等热点 | Nsight 证明值得优化 |
| Nsight Systems / Compute | 系统时间线及最耗时内核分析 | 必需的诊断能力；权限不足如实报告 |
| 对象局部 hash-grid + 小 MLP | 表达可复用的局部材质或细节函数 | 优于固定基函数的受控试验后纳入 |
| OptiX | CRF 空间函数的求交与光线调度加速 | 空间查询和可见性接口先成立 |
| NVENC / ffmpeg | 最终视频编码 | 与像素渲染质量分开测量 |

OptiX 提供可编程求交、射线生成和着色框架；它不会自动定义几何、材质或正确光传输。自定义隐式求交仍可能大量执行 CUDA 运算，不能假定整个函数求交都由 RT Core 硬件完成。[R4]

### 3.3 数值精度

几何、可见性、覆盖、HDR 累积和关键损失归约先使用 FP32；CPU 小样本参考可使用 FP64。小网络和特征矩阵可评估 BF16/FP16，并保留合适精度的主参数与优化器状态。

FP4/FP8 不作为首版几何与 HDR 质量路径的默认精度。低精度必须按算子和任务验证误差，硬件宣传的低精度峰值不能换算为本项目吞吐。

## 4. 系统架构与职责

### 4.1 GUI Service

本地工作台负责用户目标、参考素材、对象选择、局部标注、预览、质量档位、任务进度与证据查看。用户应能看到当前使用的场景版本、渲染后端、原生输出尺寸和计算预算。

输出采用渐进式显示：先结构预览，再材质/光影预览，最后高质量结果。预览精度与最终结果使用同一场景语义；近似预览必须显式标记。

### 4.2 Agent Harness

负责读取目标、生成/修改 SceneProgram、安排拟合与渲染、选择下一个值得计算的候选，并调用验证器。它不能修改封存评价集、偷偷放宽保护区或把失败记录丢弃。

默认沿用已有提议模型。模型生成期间，GPU 可以执行已经授权的候选评价和细节拟合；该后台队列有明确任务来源、预算、停止条件和优先级。

### 4.3 Compute Kernel

负责：

1. 编译稳定的对象/部件身份与算子依赖。
2. 执行几何、覆盖、材质、光照、细节和采样函数。
3. 执行参数优化与对象局部小网络拟合。
4. 返回图像、梯度、诊断通道和资源记录。
5. 对有效任务实施统一显存与执行时间管理。

一个主要 GPU 所有者进程统一管理场景、模型和内存池；HTTP/API 进程、任务协调和文件处理可以独立运行，但不各自复制同一套 CUDA 状态。

### 4.4 存储与回传

使用现有对象存储/任务记录系统保存输入、版本、函数资产、检查点和结果。执行前按内容哈希同步必需资产，连续编辑主要传输程序差异。

存储和 API 服务不承担 GPU 计算。GPU 节点通过任务队列拉取工作，先返回缩略图和诊断，再按需返回完整图片或帧序列。

## 5. 场景程序与函数表示

### 5.1 稳定的场景契约

建议新增独立 schema，保留旧格式适配：

~~~json
{
  "schema": "crf.scene.proposed.gpu96.v1",
  "scene_id": "reading-corner",
  "operator_set": "crf-native",
  "camera": {"projection": "declared", "valid_view_domain": "declared"},
  "objects": [
    {
      "id": "chair",
      "parts": ["frame", "seat", "fabric"],
      "geometry_asset": "sha256:...",
      "material_asset": "sha256:...",
      "detail_asset": "sha256:...",
      "capability": "view-bounded-relightable"
    }
  ],
  "lights": [],
  "constraints": [],
  "render_contract": {
    "native_size": [3840, 2160],
    "color_protocol": "frozen",
    "backend": "cuda"
  }

~~~

这是拟议 schema，不是声称仓库已有的可用配置。最终字段需与实际工程统一。

每个函数资产必须声明输入域、输出语义、可微参数、依赖、数值精度、可编辑参数、训练/拟合来源和局限。不能用一个无语义 RGB 输出替代全部几何与材质字段。

### 5.2 三种互补表示

| 表示 | 主要承担 | 使用原则 |
| --- | --- | --- |
| 解析/参数化函数 | 轮廓、形变、连接、重复结构和可解释约束 | 优先保留可编辑参数 |
| 自适应局部基函数/高斯 | 复杂覆盖、局部颜色或属性变化、局部修正 | 按实际误差增密、拆分与裁剪；记录全部表示成本 |
| 对象局部神经函数 | 难以用少量解析参数表达的材质与高频细节 | 使用对象坐标、局部特征与明确输出，不把光影烘入固有色 |

先保持每类对象的表示尽可能小，只有在受控评价中存在收益才增加容量。

### 5.3 神经函数的具体方向

可研究多分辨率特征表加小 MLP：输入对象局部坐标、尺度足迹及声明的对象属性，输出固有色、粗糙度、法线扰动或明确的局部几何修正。本征材质场不得把当前光源、帧号或相机像素坐标作为绕过成像计算的隐含输入；尺度足迹用于过滤和层级选择，方向相关反射通过显式材质响应接口处理。

Instant-NGP 的原始工作表明，多分辨率 hash 特征和小网络可通过融合 CUDA 计算用于不同的神经图形表示。本项目借用这一表示与计算机制，不直接移植其性能数字，也不把图像记忆能力当作材质分解能力。[R5]

同一对象在不同光照和时间下复用同一套材质身份与固定材质权重，禁止每帧重新拟合一份互不相关的 RGB 函数。验收时冻结权重和资产哈希，再进行保留光照、对象换位和局部形变，检查本征场保持和细节附着。仅有同一 ID、断网重放或哈希一致，不能证明没有记住源图。

## 6. 几何升级：分清可控 2.5D 与空间函数

### 6.1 第一层：对象局部覆盖、深度和法线

在固定视角或声明的有限视角范围内，构建：

- 轮廓和亚像素覆盖。
- 部件局部坐标与变形场。
- 局部深度、表面法线及其一致性。
- 对象间深度顺序、接触点和已观测遮挡。
- 局部厚度的明确假设或测量。
- 表面附着坐标，使纹理随物体移动。

对深度导出的法线和独立预测的法线分别标注来源；若二者共同优化，加入几何一致性约束，避免好看的高光建立在互相矛盾的表面方向上。

这层能够支持已知表面范围内的换光、形变和阴影近似，但不能完整回答离屏物体、背面或透明内部路径。

### 6.2 第二层：原生 CRF 空间查询扩展

要计算准确的离屏反射、折射、厚度吸收和多次间接光，需要新增可查询的空间表示，例如参数曲面、局部隐式函数或稀疏场。其接口至少包含：

~~~text
intersect(ray, domain) -> hit / miss / unknown
surface(hit) -> position, normal, material_id, local_coordinates, medium_boundary
visibility(a, b) -> visible / blocked / unknown
transmittance(a, b) -> RGB_transmittance / unknown
thickness(hit, direction) -> value / unknown
~~~

这是一项明确的新功能，不是给第一层增加采样就能得到。空间信息不足时返回 unknown 或声明近似，不伪造精确结果；unknown 不能自动当作 miss。透射阶段还需记录介质身份、进入/离开边界与有方向的几何法线，布尔可见性继续用于不透明对象。

该扩展仍由 CRF 函数定义并由 CRF 内核产生像素，不接入外部三维产品流水线代替。它的必要性取决于用户要验证的光学现象；第一轮固定视角质量任务可以先完成第一层。

### 6.3 隐藏结构与观测

单张照片通常不足以唯一确定背面、真实厚度、光源与材质分解。优先用多视图、多光照或用户标注约束；缺失部分标为推断，并用保留视角/光照检验。

不要把“2D Gaussian Splatting”名称视为纯二维保证；相关研究中的有向面元位于三维空间。本提案不依赖这一命名混淆。[R10]

## 7. 材质升级：让细节具有独立的物理含义

### 7.1 首批材质族

按难度分阶段实现：

1. 粗糙非金属：墙面、纸张、木材、哑光涂层。
2. 金属和涂层：拉丝方向、粗糙度变化、边缘磨损、清漆。
3. 织物：纤维方向、织纹、缝线、起伏和适当的表面响应。
4. 透明与半透明材料：只在厚度和空间可见性条件具备后进入正式验收。

建议字段包含固有色、粗糙度、金属属性、法线扰动、各向异性方向、涂层与自发光。透射、折射率和吸收系数作为空间扩展的后续字段。

不得仅给旧对象增加一组无人使用的参数；每个新增参数必须有实际 GPU 求值路径、单因素改变对照和失败检查。

### 7.2 程序细节

木纹、织纹、拉丝、微划痕、磨损和污渍通过对象坐标中的函数生成或拟合，并保持可控的方向、尺度、幅度、密度和随机种子。

细节分为：

- 影响轮廓/遮挡的几何细节。
- 影响反射方向的法线或微表面细节。
- 影响颜色与粗糙度的材质细节。

不能把所有细节混成 RGB 噪声。移动光源时，表面颜色应保持身份，高光和阴影应随光照变化。

### 7.3 反向求解

先拟合结构、轮廓、深度和几何基准法线，再拟合低频固有色、主光源与粗糙度，最后开放受约束的法线扰动和高频细节。冻结与解冻参数组有明确阶段，避免高频网络掩盖几何错误。若要报告物理意义的材料或光强数值，使用已知照明、标定参考或明确尺度归一化约定；没有这类锚点时标为相对材料/照明估计，并通过保留条件评价。

TensoIR 等反向渲染研究展示了从多视图估计几何、反射和环境光的技术方向，并讨论了阴影及间接光。它是分解设计的参考，不证明本项目已实现，也不能外推成单图中所有复杂材质都能唯一恢复。[R6]

## 8. 光照升级：从直接光到受控的多次光传输

### 8.1 可先完成的部分

- 方向光、点光和面积光的明确语义。
- 可复现的光源采样与软阴影。
- 固有色与光照分离。
- 可见性、接触阴影和有限表面反射。
- 线性 HDR 计算，最后统一曝光、色调映射与显示编码。

如果使用环境光函数，记录其来源和表示。参考环境图可以作为已声明的照明观测，不能作为画面背景贴图偷偷带入结果；最终环境表示与推断成本纳入资产账本。

### 8.2 空间扩展后的部分

- 镜面和粗糙反射。
- 多次漫反射与颜色互染。
- 透射、折射与吸收。
- 必要时的稀疏体积效果。

先实现正确的简单积分器和独立参考，再加入重要性采样、多种采样策略结合与分波次队列。极端焦散、高复杂度体积和任意人像皮肤不作为首个版本的默认承诺。

### 8.3 采样与输出策略

渲染从低采样渐进到高采样。试验可使用每像素 64、256、1024 样本档位和 1、2、4 次反弹档位，但只有已经实现相应光传输时才启用；这些是比较预算，不是预先保证的质量值。

为保持可重复性，随机序列由场景、像素、样本序号和种子决定，尽量不随 tile 尺寸或候选批次变化。

保留未去噪的原始线性结果及收敛曲线。可选去噪必须单列输出和误差，不能用锐化、超分或去噪细节代替原生求值的证据。

## 9. 多尺度细节与高分辨率

### 9.1 以图像足迹控制细节

使用对象坐标的连续函数和尺度相关过滤。视图缩小、远离或运动时，对高频细节进行正确过滤；近景才逐渐展开可见的高频。

Mip-Splatting 的原始研究关注采样尺度变化产生的混叠问题，并使用频率约束与像素过滤。本方案借鉴“细节应与采样足迹匹配”的原则，不假定其三维算法已移植到 CRF。[R7]

### 9.2 原生输出

先验证 2048 级长边，再验证 3840 × 2160。最终高分辨率必须重新求值函数和积分；输出更大的文件或把低分辨率插值放大不算完成。

提供原生图、100% 局部裁切、边缘图和必要的诊断通道。全图与分块渲染需要在相同采样协议下比较，检查 tile 接缝。

### 9.3 时间维度

使用稳定对象 ID、局部坐标和固定程序随机种子。动画中共享几何与材质资产，时间只改变明确的状态变量。阴影、反射和可见性缓存随依赖变化失效。

视频使用有限环形缓冲与流式编码；不把全部帧常驻显存作为“使用大显存”的手段。任意时刻单独重载程序求值，应与对应编码前视频帧按同一合同核对。LOD 和采样状态由程序及时间确定；历史缓存必须显式记录并可重建。导出期间冻结函数权重，保留未经时间滤波的结果供核验。

## 10. 96 GB 显存如何真正使用

### 10.1 计量口径

所有调度判断使用运行时返回的字节数。界面同时显示 GB 和 GiB：

- 1 GB = 10^9 bytes。
- 1 GiB = 2^30 bytes。
- 用户所述 96 GB 是设备规格，不能未经读取就硬编码为 96 GiB。

至少记录四项：

1. 设备总使用量：包含本进程、驱动/上下文、外部扩展以及其他进程。
2. 框架 live allocated：正在由活跃张量占用的内存。
3. 框架 reserved：缓存分配器管理的内存，不能再与 allocated 相加。
4. 按资产/任务归属登记的有效工作集与可回收缓存。

PyTorch 的未使用缓存也可能显示为 nvidia-smi 已用；empty_cache 释放闲置缓存，但不会释放仍被张量占用的内存。因此仅提供 nvidia-smi 截图不足以证明有效利用。[R8]

### 10.2 整卡预算

令 M 为实际可见显存；E 为测得的非 CRF 驱动、上下文和其他驻留占用；G 为安全余量。CRF 的动态预算为：

~~~text
g = 0.10（默认）；独立压力校准后才可设为 0.08
G = max(g × M, 尚未计入工作池的额外峰值 + 碎片与不确定余量)
B = M − E − G
~~~

已知的临时工作区、新旧资产同时驻留和重分配峰值都计入 B 内的任务峰值；G 覆盖尚未计入其中的额外峰值与不确定性。E 只统计没有记入任何 CRF 池的占用；已经计入工作池的自定义 CUDA/OptiX 缓冲不再重复扣除。不能先让 CRF 分配 90%，再把驱动与其他使用叠加在外。

默认设备使用上限约为 90%。只有独立压力验证后，才可将 guard 从 10% 调到 8%；92% 作为经验证配置的上限，不能与“仍有 10% guard”同时宣称。任何模式都计算旧新缓冲同时存在的重分配峰值。

### 10.3 三种工作模式的软预算

下面的比例是 **B 内部的可借用软预算**，每列合计 100%。实际字节由调度器按实测 B 计算；不是启动时预分配所有池。

| 用途 | 拟合 Fit | 最终渲染 Render | 搜索 Search |
| --- | ---: | ---: | ---: |
| 几何/材质/细节函数及共享资产 | 18% | 32% | 22% |
| 梯度、主参数与优化器状态 | 24% | 0% | 16% |
| 活跃样本、特征与中间激活 | 24% | 28% | 18% |
| 参考观察、多尺度特征缓存 | 12% | 8% | 10% |
| 像素累积、诊断通道和帧缓冲 | 10% | 24% | 12% |
| 质量评价、候选增量与其他工作区 | 12% | 8% | 22% |
| 合计 | 100% | 100% | 100% |

例如运行时测得 B = 80 GiB，拟合模式中函数资产约 14.4 GiB、优化器状态约 19.2 GiB、激活约 19.2 GiB、观察缓存约 9.6 GiB、图像通道约 8 GiB、评价/工作区约 9.6 GiB。**这个例子只展示预算算法，不是对用户设备实际空闲量的测量。**

首版云端 LLM 权重预算为 0。评价模型按需加载，其权重与激活包含在评价池中，不额外绕过总预算。

### 10.4 给显存安排有效工作

优先按以下顺序扩展：

1. 保持当前任务真正需要的对象函数、观测金字塔和共享资产驻留，减少反复传输。
2. 增加像素/表面样本微批次，直到吞吐不再改善。
3. 增加独立对象、参数假设或场景候选的批量评价。
4. 对误差集中且有观测支持的区域增加函数容量和细节尺度。
5. 在预算内加密阴影、反射和高方差区域采样。
6. 执行已经排队的同项目有效任务，包括开发/选择验证和跨帧一致性检查；正式封存集只按 GPU-M6 的预注册协议调用，不能为占用 GPU 反复试验。

每一步都记录收益。没有吞吐、质量或缓存命中收益时停止扩展，释放或借出预算。

### 10.5 为什么分辨率本身用不完 96 GB

一张 3840 × 2160 的 RGBA FP32 缓冲仅约 126.6 MiB。高质量渲染的大工作集来自函数表示、优化状态、路径/样本批次、激活和多个同时有效的对象，而不是最终图片本身。

反过来，直接构造“4K 全部像素 × 65,536 个高斯”的单个 FP32 数组约为 2.17 TB，96 GB 也无法承担。因此仍必须进行空间分桶、tile 裁剪和流式累积。

### 10.6 禁止无效填充

以下行为不得计为硬件利用成果：

- 分配未使用的大张量。
- 多个进程复制同一个模型或不可变场景。
- 保留从未命中的缓存。
- 为了显存占用而取消已有的有效分块。
- 扩大网络而没有独立验证改善。
- 无限增加样本，却不测量收敛。
- 创建同质候选，使“候选数量”虚增。

## 11. 调度、并行和热点优化

### 11.1 三类队列

- 交互队列：预览、局部编辑、取消；最高优先级。
- 高质量队列：当前用户要求的拟合和最终渲染。
- 后台队列：已授权项目内的候选评价、细节优化和 RSI 实验。

后台任务必须有 GPU 秒、候选数量和保存检查点的上限。GPU 空闲不构成擅自开展无边界后台训练的授权。

### 11.2 批量自适应

对代表任务扫描微批大小，例如从 2^18 个样本逐步到 2^22；从 2、4、8 个驻留拟合对象开始扩展；从少量候选扩到 8、16、32、64 个候选的分阶段评价。它们都是搜索档位，不是同时常驻的硬性配额。

分开记录 microbatch 与优化器 logical batch。单纯改变微批和梯度累积时维持同一逻辑批、总渲染样本量、随机样本 ID 与更新规则；按有效样本数加权归约，正确处理尾批。内存压力先降低同时活跃的工作量，不暗中减少承诺的总计算。统计优化规则若改变，另设实验，避免误算为 GPU 加速。

调度器每个校准窗口比较有效样本/秒、合格候选/秒、画质变化、P95 响应和峰值内存。更多并发开始降低效率时回退。

### 11.3 共享资产与增量候选

候选共享不可变几何、参考特征、材质基底和编译结果，仅保存变化参数与必要优化器状态。使用 SoA 等适合批量访问的数据布局，避免每个像素通过 Python 遍历对象。

候选先以低分辨率和有限采样筛选，再给少量优胜者高质量预算。总成本包括所有被淘汰候选。

### 11.4 设备侧流程

几何求值、覆盖、材质、光照、合成和评价尽量保持在 GPU 上。减少每轮把图像传回 CPU 再计算损失的往返。

可采用分块队列、异步传输、固定形状批次和稳定阶段的 CUDA Graph；只有时间线证明有收益时启用。所有 stream 依赖和缓冲生命周期显式管理。

共享内存、寄存器压力、warp 分歧和显存带宽可能成为瓶颈。Nsight 指出 occupancy 更高不必然更快，因此不设“所有硬件单元都必须达到同一百分比”的伪指标。[R9]

## 12. 拟合、评价与 RSI

### 12.1 分阶段优化

1. 观测准备：固定色彩/曝光处理，划分开发观测与保留观测。
2. 几何阶段：轮廓、部件、接触、深度关系和几何基准法线。
3. 低频材质与光照：固有色、主光源、粗糙度。
4. 局部细节：法线细节、纹理函数和小网络参数。
5. 联合微调：只开放已经过验证的参数组。
6. 独立评价：新光照、有限新视角、局部编辑和时序。

损失包含线性域重建、边缘、结构/连接、材质与光照一致性、尺度与时间一致性。感知指标可作辅助，不能单独决定通过。损失权重和评价集在正式比较前冻结。

连续且可微的参数使用梯度等连续求解；部件缺失、连接拓扑和函数类型由离散搜索或模型修订处理。遮挡切换等不连续点需要声明近似或采用外循环，不能把所有成像误差都承诺为自动可微解决。任何近似求解得到的候选，最终回到同一发布前向内核验收。

### 12.2 两条质量轨道

**重建轨道：**用给定参考拟合对象/场景，测 PSNR、SSIM、边缘误差、保留光照与编辑后的结构表现。

**新创作轨道：**模型组合可调用函数生成新场景，采用盲评和对象/光照约束；不能因为能拟合照片就宣布任意新构图生成已解决。

网络检索可以提供观察与先验，但其来源、许可、训练/评价划分和实际调用必须记录。检索图片的数量不能作为生成质量指标。

### 12.3 RSI 保持独立

GPU 上允许更多程序候选和算子变体，但“多试一些参数”不能自动计为程序级 RSI。

真正的 RSI 候选应改变可执行算子、求解策略或程序结构，经过冻结评价、回归与数值检查后晋升；后续新任务实际调用晋升版本。保存提议、代码差异、测试、成本、晋升与回滚记录。

### 12.4 形式证明与有限验证

继续区分：

- 符号/约束性质：参数域、变形连接、程序类型等。
- 数值符合性：CPU 与 GPU 的指定输入和误差合同。
- 有限实例性质：某场景、某后端和某编辑下的检查。
- 感知质量：实测与人工评价，不能由形式证明代替。

CUDA 内核、浮点模式、编译器或采样改变后，旧证明不能自动覆盖新后端。

## 13. 编辑保护与全局光照的依赖

局部编辑可能通过阴影、反射和间接光影响远处像素。因此新增光照能力后，脏区应根据依赖图扩展；不能继续只用物体包围盒当成完整影响范围。

如果用户同时要求某一区域逐字节冻结，而物理一致的光照传播需要改变该区，系统应说明合约冲突，并保留已批准的编辑约束。不能偷偷扩大影响范围来绕过冻结要求。

CPU/GPU 跨后端采用数值容差，不承诺逐字节恒等。原 1.1 的最大通道误差 2/255、P99 1/255 可作为旧算子支持域的初始建议，需在 GPU-M0 冻结；新增 HDR、随机积分和空间函数需要各自独立合约。[P2]

同一后端的保护区、完整重算与脏区更新另行检查。保存缓存 tile 字节不等于证明该区域在完整物理重算中本来不该变化。

## 14. Worker、任务与证据接口

以下是拟议接口，实施时适配现有服务：

| 任务 | 输入 | 输出 |
| --- | --- | --- |
| object-fit | 观测、对象/部件、允许优化参数、阶段与预算 | 函数资产、参数、小网络权重、训练/保留指标 |
| material-fit | 几何、不同照明观测、材质族与约束 | 材质字段、换光验证、可辨识性与假设记录 |
| candidate-eval | 候选程序、共享资产、评价版本、总预算 | 预览、评分分项、约束、成本与筛选记录 |
| frame-render | 场景、相机、时刻、分辨率、采样合同 | 原生图、线性图、诊断通道、性能与摘要 |
| sequence-render | 同一场景的时间状态、帧采样和编码设置 | 帧序列、视频、跨帧验证与编码记录 |

建议端点覆盖提交任务、读取状态/事件、取消/恢复和获取资产；不把长任务放在单个同步请求中。

每次任务保存：

~~~text
JobSpec
  input_hashes, scene_hash, kernel_build, operator_version
  device_uuid, driver, runtime, compiler, precision
  native_size, sampling, color_protocol, seeds
  requested_budget, measured_gpu_time, actual_samples
  actual_parameters, representation_bytes, observation_sources
  memory_ledger, device_trace, stage_timings
  quality_metrics, contract_results, failures, checkpoint
  output_hashes, promotion_or_rejection
~~~

源观察在拟合结束后可从最终渲染进程的可读资产集合中移除，验证渲染只依赖声明的场景和函数资产。保留外观重建与可换光资产的不同能力标签。

## 15. 性能与画质验收

### 15.1 先冻结比较条件

固定场景、输入、相机、曝光、色彩协议、评价版本、模型提议来源、随机种子和输出尺寸。所有候选、失败与重试计入总预算。

### 15.2 核心对照

| 组别 | 条件 | 用途 |
| --- | --- | --- |
| CPU-Ref | 原算法、原设置、参考执行 | 数值与语义基线 |
| GPU-A | 同算法、同设置、GPU 执行 | 正确加速 |
| GPU-B | 同算法、提高预算 | 计算量收益 |
| GPU-C | 新算法，与 B 相同时间/费用预算 | 算法收益 |
| GPU-D | 与 C 相同基础系统及总预算，开启受限 RSI | RSI 的额外收益 |

若更换提议模型，另设模型对照，不混入 GPU 加速结论。

增加 24、48、72 GB 逻辑容量限制与完整整卡预算的实验，测量同卡上更大工作集的贡献。容量限制作用于 CRF 应用池，即各组可用预算为 min(B, 指定容量上限)，驱动/外部占用口径与 guard 不变；完整整卡组使用完整 B。记录实际使用量与是否启用了重计算/卸载。该比较只说明容量限制的影响，不能称为不同型号 GPU 的性能对比。

### 15.3 三类正式结果

**质量：**原生图与局部裁切、参考误差、几何/接触/材质/换光分项、尺度与时间稳定性、编辑后保持情况。

**性能：**冷启动和预热后延迟、中位数/P95、有效样本/秒、合格候选/秒、上传/下载和编码时间。CUDA 事件用于 GPU 阶段计时；端到端墙钟时间另报。剖析开销与正常运行计时分开。

**资源：**device used、allocated、reserved、外部分配、峰值/持续工作集、缓存命中、CPU 内存、传输量、GPU 秒及可获得的能耗。

有待执行工作时，稳态 GPU 活跃时间比例 85% 可作为调查目标；它不是算力效率的充分证据。必须解释最耗时内核的计算或带宽限制，以及继续增加批次是否仍有收益。

### 15.4 稳定性门槛

建议在冻结的代表场景组合上运行至少 2 小时的高质量/拟合混合任务，完成取消、恢复、检查点重载和任务切换。正式通过条件包括无未处理 OOM、无错误结果静默晋升、无持续显存增长、无保护区规则绕过。

这是拟议验收时长，不是本次已运行的测试。安全余量的校准要覆盖最大形状、编译工作区和新旧资产同时驻留的峰值。

### 15.5 正式视觉评价

首轮 3 类场景用于工程开发。正式照片质量宣称沿用原 1.1 的独立来源原则，目标至少 20 个独立目标，每组至少 3 名有效人工评审，报告场景级胜率和不确定区间。不能由模型填写人类盲评结果，也不能把同一照片的多次裁切当独立场景。

新算法收益、更多算力收益和回退后的不回归分别报告。对接近零的误差采用事先冻结的绝对阈值。

## 16. 代表场景与演示要求

### A. 温暖的临窗阅读角

木桌、金属台灯、布艺座椅、纸张与书籍。验证木纹方向、金属高光、织物细节、部件接触、窗光软阴影和对象相互遮挡。

操作：替换台灯材质、移动光源、改变椅背比例、局部修正织纹。输出原生 2K/4K 及相同裁切。

### B. 雨后石阶庭院

石材、湿润表面、植被和远近层次。验证多尺度细节、粗糙度空间变化、细枝/叶片覆盖、局部反射与色彩层次。

明确有限视角与空间信息范围；未经空间验证的水面反射不能当成真实光传输结果。

### C. 工具与材料静物

金属工具、木材、织物或皮革，使用多个受控光照照片。几何和光照变化后检查材质身份、接触和局部细节。将其中一组光照封存，只用于最终评价。

现有杯子与订书机可作为回归用例，不继续作为新画质能力的主要证明。

## 17. 分阶段实施与停止条件

| 里程碑 | 核心工作 | 可交付结果与通过门槛 |
| --- | --- | --- |
| GPU-M0 设备与合同 | 读取整卡资源、兼容环境、基线计时、冻结评价协议 | hardware-profile、环境锁定、场景与预算清单；明确真实可见显存 |

| GPU-M3 整卡调度 | 三模式预算、批量对象/候选、缓存、取消/恢复 | 容量限制对照、有效吞吐曲线、稳定性记录 |
| GPU-M4 真实场景与原生 4K | 已支持的 2.5D/直接光场景、尺度与时序、工作台集成 | 原生图/裁切/视频、交互记录、完整重算和依赖验证；需要空间查询的反射/透射/间接光子项等待 GPU-M5 |
| GPU-M5 空间光传输 | 仅按目标需要新增空间查询、反射/透射/间接光 | 独立求交/可见性/积分验证与保留光照；未覆盖的能力明确保留为未知 |
| GPU-M6 RSI 与正式封存 | 算子/求解策略晋升、独立目标评价、版本发布检查 | 真实程序级收益、旧任务回归、后续新任务继承、完整编辑器可运行 |

GPU-M2 的直接光任务可以与 GPU-M3 并行推进；GPU-M5 以空间表示、观测和独立参考成立为前提。GPU-M6 的正式封存等待必要前置门槛完成。

每个里程碑失败时输出具体差距和已有证据，不改小目标、不回退版本号、不用新文档或显存截图代替功能完成。
