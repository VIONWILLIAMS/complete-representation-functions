# 这些图片的像素，是怎样由代码算出来的？

这次实际完成的路线是：**先用代码搭建一个三维场景，再计算这个场景在指定相机和灯光下的成像。** Python 负责搭场景，C++ 负责追踪光线，最后的显影程序把高动态范围数值变成可显示的 PNG。实际生成了哪些图、用了多长时间，以成图清单和逐图 JSON 为准。

## 1. 先搭一个数字摄影棚

程序要明确告诉计算机：桌子在哪里、瓶子是什么形状、玻璃有多厚、太阳从哪里照过来、相机对焦在哪儿。

本实验的花瓶和玻璃瓶来自一条轮廓线绕轴旋转；布料是一张带褶皱的曲面网格；山体与沙丘由高度函数生成。它们最后都变成渲染器能够求交的几何。

材质也是规则。木材的颜色随三维坐标变化，玻璃指定折射与吸收参数，黄铜使用金属反射模型。这里使用的木纹、石纹和沙纹来自数学函数。具体实现可查看 `scenes/` 和 `src/renderer.cpp`。

这意味着，“代码生成图片”仍然需要大量场景设计。单有一个很快的渲染器，不能自动得到自然的树叶、可信的布料或好看的构图。

## 2. 每个像素都向场景提出一个问题

可以把相机的一个像素理解成一个很小的观察窗口：

> 从这个窗口看出去，哪些物体和光源会把多少光送进来？

程序先从相机发出一条射线，找出它首先碰到的表面。这里的“从相机出发”是计算顺序；真实光能仍然来自光源。

如果首先碰到陶器，就计算陶器反射来的光；碰到玻璃，要决定反射还是折射，并继续追踪后面的物体；碰到金属，则按表面粗糙程度计算反射方向。光线经过多次相遇，累积出这一条路径对像素的贡献。

BVH 可以理解成场景的分区索引。判断射线可能经过哪些大区域，再检查这些区域内的小物体，可以少做很多无用的求交计算。本实验的 CPU 和 CUDA 原型都实现了软件 BVH。

## 3. 为什么一个像素要计算很多次？

一个表面会接收许多方向的光。把所有可能光路一条不漏地算出来，代价极高，因此路径追踪会抽样计算，再求平均。

下面只是解释计算关系的伪代码，实际入口位于 `src/renderer.cpp`：

```python
for pixel in image:
    accumulated_light = 0
    for sample in range(samples_per_pixel):
        ray = sample_camera_ray(pixel, lens, focus, random_seed)
        accumulated_light += trace_light_path(scene, ray)
    linear_image[pixel] = accumulated_light / samples_per_pixel
```

`256 spp` 表示每个像素采样 256 次。2048 × 2560 的图像一共有 5,242,880 个像素；使用 256 spp 时，会发起 **1,342,177,280 条相机路径**。每条路径还可能经过多次反射或折射。这是代码中宽、高与 spp 的乘积，不等于实际射线求交次数。

样本较少时，随机估计有波动，画面就会出现颗粒、暗部噪声或少量特别亮的点。增加采样通常能减少噪声，但不会改变花瓶的形状、树叶的复杂度或木纹的设计。

## 4. 玻璃为什么能看起来透明？

透明并不是把一个颜色的透明度降低。本实验会计算光线进入和离开玻璃时的方向变化，并按传播距离衰减光能。反射与透射的比例随观察角度变化，所以瓶子的正面、边缘和瓶底会呈现不同的亮暗和形变。

这里仍有明确近似：使用 RGB 光学与理想介电表面，没有完整的光谱色散、复杂镜组或任意嵌套介质系统。瓶子的几何分段、法线和材质近似，都可能在高光中暴露出合成感。

## 5. 为什么还要有“显影”？

渲染器输出的是线性光能数值，范围可以超过显示屏能呈现的亮度。原始 PFM 和对应的 32 位浮点 EXR 保留这部分信息；显示 PNG 要经过曝光、色调曲线与 sRGB 变换。

本轮还使用了可审查的传统局部滤波：参考相邻像素的颜色、表面方向、材质色和深度，降低噪声。静物图另有一项保护玻璃/金属主表面的离群亮点抑制。它在原始线性数据上只降低 167 个孤立峰值，随后重新显影；全部参数、像素位置、采用前后对照与原始 HDR 均保留。

这种显示滤波带有偏差，可能弱化真实但尚未充分采样的焦散。因此，展示图更干净不能直接证明光照计算更准确。所有图片保持原始渲染尺寸，没有使用超分辨率。

## 6. GPU 在这里负责什么？

许多像素和样本可以同时计算。CUDA 后端把这批计算分配给大量 GPU 线程，场景、BVH、路径状态和图像缓冲则存放在显存里。

96GB 显存能够容纳更大的场景和缓冲，但“用了多少显存”不是成像质量的评分。实际性能需要在目标机器上测量：一秒完成多少工作、GPU 利用率如何、有没有内存或寄存器瓶颈，以及相同参数下的图像是否正确。

本轮 GPU 源码已在本机隔离的 NVIDIA CUDA 13.0.88 工具链下完成 `sm_120` 交叉编译与链接。**编译通过只说明这套源码可以在该工具链中生成程序。** GPU 执行、远端 CUDA 12.8 兼容性、CPU/GPU 一致性和性能，都需要在真正连接的目标机器上继续验证。状态证据见 `logs/cuda_compile_status.json`。

## 7. 如何证明图片确实受代码控制？

本实验保留了三类证据：

- **生成链路：**场景代码、渲染器源码、参数、随机种子、运行日志和文件哈希。
- **几何证据：**法线与深度辅助图直接来自射线求交，能够检查表面方向与物体距离。
- **参数实验：**固定相机、几何和随机种子，只修改玻璃的传输颜色，再重新运行。图像颜色随之变化，而法线与深度原始数据的哈希保持一致。记录见 `logs/controlled_parameter_check.json`。

这些证据支持“本轮样片由这套程序生成”的结论。照片级质量还要单独评审：模型是否自然、材质是否可信、细节是否充分、光照是否合理，以及放大后是否出现明显的几何和采样问题。
